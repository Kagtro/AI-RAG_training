# RAG 项目优化路线图

> 版本：v1.0（2026-11-05）
> 基线：当前 `AI-RAG_training` 项目
> 目的：把"能跑"变成"可信、可讲、可维护"，避免盲目堆功能

---

## 1. 当前基线

| 项 | 现状 |
|---|---|
| 语料 | 6 份公开法律法规，约 85 个 chunk |
| 解析/清洗 | PDFBox/POI + TextCleaner（去页眉页脚/页码/断行） |
| 切片 | 按页 + 段落聚合 + 700 字 + 120 overlap |
| 向量化 | text-embedding-v3，1024 维 |
| 召回 | 向量 + BM25 + RRF；多意图查询拆解 |
| 生成 | qwen-plus，SSE 流式，引用对齐 |
| 评测 | 70 题：39 可答 / 17 跨文档 / 14 不可答 |
| 评测结果 | Recall 1.0、跨文档 1.0、引用覆盖 1.0、拒答 1.0、P95 8.7s |
| 工程 | 单体 Spring Boot，无鉴权、无测试、无 CI、无监控 |

### 核心判断

1. **当前瓶颈不是切片**：70 题已全 1.0，切片不是主要矛盾；
2. **最大风险是评测饱和**：自己出的题贴合当前实现，1.0 不能证明真实效果；
3. **第二差距是工程化**：没有测试、CI、容器化、日志指标，面试可信度不足；
4. **平台化功能（工作流、多租户）性价比低**，不建议现在做。

---

## 2. 目标与非目标

### 目标

- 让评测**可信**：有难例、有失败分析，不是"全 1.0"；
- 让工程**可信**：核心逻辑有测试，能一条命令跑起来；
- 让 RAG 有**可讲的一个深度点**：结构切片/父子块或 rerank（二选一）；
- 不引入无法维护的复杂度。

### 非目标（当前明确不做）

- 不做 Dify/RAGFlow 式的工作流编辑器；
- 不做多租户/复杂 RBAC（除非目标岗位明确要求）；
- 不做分布式索引、Kafka、K8s；
- 不为了"技术含量"重写成 LangChain4j/Spring AI；
- 不盲目上语义切片。

---

## 3. 优先级总览

| 优先级 | 事项 | 价值 | 成本 | 建议 |
|---|---|---|---|---|
| **P0** | 难例评测 + 失败分析 | 很高 | 1 天 | 立刻做 |
| **P1** | 核心单测 + Docker + CI | 高 | 1 天 | 立刻做 |
| **P1** | `qa_log` / 日志指标 | 中 | 半天 | 有空做 |
| **P2** | 结构感知切片 + 父块 | 中高 | 1–2 天 | 做完 P0/P1 再评估 |
| **P2** | Rerank | 中 | 1 天 | 等难例证明有价值再做 |
| **P3** | 鉴权/多知识库 | 高（企业） | 2–3 天 | 看岗位 |
| **P3** | OCR/表格/多格式 | 中 | 2–3 天 | 真实 PDF 场景再做 |
| **P3** | 工作流/多租户 | 低（个人项目） | 很大 | 不做 |

---

## 4. P0：难例评测与失败分析

### 4.1 为什么先做

当前 70 题全 1.0，有两个问题：

- 题目和当前实现太"贴合"，没有区分度；
- 指标饱和后，无法判断后续优化是否有效。

**先让评测"能失败"，优化才有意义。**

### 4.2 任务清单

- [ ] 从 70 题中保留 50 题作为基础集；
- [ ] 新增 20–30 道**难例**（总量 90–100；如果不想扩太多，至少 10 道）；
- [ ] 每题标注：类型、必选文档、可选文档、标准答案、关键词；
- [ ] 增加"失败原因"字段（人工分析时填写）；
- [ ] 评测报告按类别拆分：可答 / 跨文档 / 不可答 / 难例；
- [ ] 选 5–10 条做人工抽检，记录"关键词判分"的误判。

### 4.3 难例类型

| 类型 | 例子 | 考察点 |
|---|---|---|
| 同义改写 | "试用期最长能设多久" vs "试用期上限" | 语义召回 |
| 精确编号 | "《社会保险法》第三十三条内容" | BM25 / 精确匹配 |
| 长问题 | 一段包含两个以上子问题 | 查询拆解 |
| 跨文档 | 合同 + 社保 + 公积金组合 | 多路召回 |
| 否定/边界 | "哪些情形**不**认定为工伤" | 生成与理解 |
| 不可答 | "2026 上海社保基数上下限" | 拒答 |
| 模糊指代 | "这个条例里说的年休假怎么算" | 上下文/查询改写 |
| 多跳 | 先查制度，再查例外 | 多跳拆解 |

### 4.4 指标与报告

- 分类指标：可答 Recall、跨文档 Recall、难例 Recall、拒答率；
- 引用覆盖：必选文档覆盖；
- 答案正确率：关键词 + 人工抽检；
- P95 / 平均延迟；
- **失败清单**：题号、问题、召回结果、引用、答案、失败原因。

### 4.5 验收标准

- 评测集 ≥ 90 题（至少 20 道难例）；
- 至少 5 条失败案例有原因分析；
- 报告里能看到"哪类问题弱"，而不是只有一个总分；
- 面试能讲出 2–3 个具体失败案例和修复思路。

### 4.6 产出

```
eval/eval_cases.csv       # 扩充后的评测集
eval/load_eval.sql        # 导入脚本
eval/README.md            # 新增难例说明
eval/report-latest.csv    # 评测明细
docs/failure-analysis.md  # 失败案例分析（新建）
```

## 5. P1：工程化

### 5.1 核心单元测试

优先测"纯逻辑、无外部依赖"的类：

| 测试对象 | 用例 |
|---|---|
| `ChunkingService` | 段落聚合、700 字上限、overlap、单行超长 |
| `TextCleaner` | 页眉页脚、页码、断行合并、全角转半角 |
| `QueryDecompositionService` | 多意图判断、规则兜底 |
| `EvalService` | Recall/groundedness/关键词匹配 |
| `ChatService` | 引用解析、越界清理、对齐 |

命令：

```powershell
mvn test
```

### 5.2 Docker 化

- 写 `Dockerfile`（多阶段构建）；
- `docker-compose.yml` 增加 `app` 服务；
- 一条命令启动：

```powershell
docker compose up -d
```

### 5.3 CI

- GitHub Actions：`mvn -q test`；
- 可选：构建镜像并推送（先不做也行）。

### 5.4 可观测性

- `qa_log` 落库：问题、召回 ids、答案、延迟、token、成本；
- 日志记录：检索耗时、生成耗时、引用数量；
- 可选：``/actuator/metrics``。

### 5.5 验收标准

- `mvn test` 全绿；
- 新机器 `docker compose up -d` 能启动应用；
- CI 通过；
- 能从日志/`qa_log` 查到一次问答的耗时和引用。

## 6. P2：RAG 深度优化

### 6.1 结构感知切片 + 父块（首选）

**为什么**：法律文档天然按"第 X 条"组织，比 700 字硬切更贴近语义。

做法：

1. 新增 `ArticleChunker`（或给 `ChunkingService` 加 strategy）；
2. 按行首 `第X条` 切分；
3. 条太长再按段落切；太短可按章节合并；
4. 检索用条级 chunk，生成时返回父章节（父块）；
5. 重建索引，跑同一套 90+ 题评测对比。

验收：

- chunk 中条款完整率提升；
- Recall 不下降；
- 引用能定位到具体条款；
- 有前后对比数据。

### 6.2 Rerank（条件做）

**为什么暂缓**：当前 Recall 1.0，rerank 没有提升空间。

触发条件：

- 难例集显示"候选里有答案但排不进 topN"；
- 或召回的 topK 噪声明显。

做法：

- 召回 top 20–30 → cross-encoder/托管 rerank → top 3–5；
- 对比答案正确率、引用覆盖、P95 延迟、成本。

### 6.3 鉴权 / 多知识库（看岗位）

- Spring Security + 用户/角色；
- `kb` 增加 owner、ACL；
- 上传/检索按用户过滤；
- 前端登录页。

只有目标岗位明确要求"企业级/权限"时再做。

### 6.4 解析增强

- OCR（扫描版 PDF）；
- 表格结构化；
- 更多格式（HTML、PPT、Excel）；
- 文档版本/去重。

真实 PDF 场景遇到问题再做。

---

## 7. P3：不建议现在做的

| 功能 | 原因 |
|---|---|
| 可视化工作流 | 和 RAG 核心能力关系小，投入大 |
| 多租户 SaaS | 个人项目不需要 |
| 分布式任务队列 | 单机 6 文档用不上 |
| 语义切片 | 法律文档结构清晰，按条切更划算 |
| 重写成 LangChain4j | 会隐藏实现细节，面试反而不利 |

---

## 8. 时间安排（按面试优先级）

### 如果只有 2 天

1. 第 1 天：难例评测 + 失败分析；
2. 第 2 天：核心单测 + Docker 化；
3. 不碰切片/rerank。

### 如果有 5 天

1. 第 1 天：难例评测；
2. 第 2 天：单测 + Docker + CI；
3. 第 3 天：结构切片 + 父块；
4. 第 4 天：评测对比 + 失败分析；
5. 第 5 天：文档/简历更新。

### 如果有 1 周以上

- 再考虑 rerank、鉴权、OCR；
- 仍然不建议做工作流平台。

---

## 9. 风险与停止条件

| 风险 | 应对 |
|---|---|
| 难例集做完指标下降 | 正常，说明评测变真实；先记录失败类型 |
| 切片改动导致效果下降 | 保留旧策略开关，A/B 对比，不达标就回退 |
| rerank 延迟过高 | 控制候选数、加缓存、只在难例启用 |
| 工程化占用太多时间 | P0/P1 各 1 天封顶，优先保证面试 |

**停止条件**：如果某项优化 1 天内没有可展示的评测对比，就暂停，回到面试准备。

---

## 10. 面试叙事

> "我的项目已经跑通 RAG 全链路，并且做了查询拆解、混合检索、引用对齐和 70 题评测。当前指标全 1.0，但我认为这个数字不可信，因为题目是自己出的。所以我下一步不是继续堆功能，而是先补难例评测和失败分析，再做工程化测试和容器化；切片/rerank 这类优化会等评测暴露问题后再做。"

这段话体现的是：

- 知道当前成果；
- 知道指标的局限；
- 有优先级判断；
- 不盲目追求技术复杂度。
