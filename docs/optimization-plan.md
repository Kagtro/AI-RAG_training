## 1. 优化前的基线

| 项 | 初始状态 |
|---|---|
| 语料 | 6 份公开法律文档，约 85 个 chunk |
| 解析/清洗 | 仅有基础换行归一化 |
| 切片 | 700 字 + 120 overlap，按页/段落 |
| 检索 | 仅向量召回，topK=5，阈值 0.1 |
| 生成 | qwen-plus，基础 Prompt + 引用解析 |
| 评测 | 30 题，指标接近全 1.0 |
| 工程 | 无单测、无 CI、无容器化、无问答日志 |

当时最大的问题不是"功能少"，而是：

1. 评测太简单，指标饱和，无法判断优化是否有效；
2. 单向量检索对多意图/跨文档问题召回不足；
3. 引用经常把法条编号当片段编号，引用覆盖低；
4. 没有工程化证据（测试/CI/日志）。

## 2. 优化时间线

| 阶段 | 改动 | 解决的问题 | 结果 |
|---|---|---|---|
| 1 | 引用对齐 + 清理越界编号 | 模型写 `[10]`、引用为空 | 引用覆盖率 0.50 → 0.96 |
| 2 | 混合检索：向量 + BM25 + RRF | 专有名词、条款号召回弱 | 提升字面匹配召回 |
| 3 | 多意图查询拆解 | 一个向量被单个意图主导 | 跨文档题可覆盖多份文档 |
| 4 | 评测集扩到 150 题（80 难例） | 评测饱和、无失败样本 | 指标从"全 1.0"变得可分析 |
| 5 | Prompt v2：否定结论/未规定不推断 | 拒答过度、拒答不足 | 难例通过率提升 |
| 6 | 多查询覆盖注入 + 引用补齐 | 三份文档只引两份 | 跨文档召回/引用覆盖到 1.0 |
| 7 | 阈值扫描 0.1/0.3/0.5/0.7 | 阈值靠拍脑袋 | 默认改 0.5，P95 降低 |
| 8 | 单测 + Docker + CI + qa_log | 工程可信度不足 | 9 个测试、CI、一键启动 |

## 3. 关键决策

### 3.1 为什么做混合检索

- 向量擅长语义相近，但对"第三十三条""公积金"这种精确词不稳定；
- BM25 擅长字面匹配，但不懂同义改写；
- 两路各取 topK，用 RRF 按排名融合，避免分数量纲问题；
- 中文 BM25 用字符二元组，暂不引入分词器。

### 3.2 为什么做查询拆解

- 多意图问题（"签合同和公积金登记的时限分别是多久"）用一个向量表示，会被其中一个意图主导；
- 先判断是否多意图，命中才调 LLM 拆成 2~3 个子问题；
- 每个子问题分别召回，再用 RRF 融合；
- 每个子查询的向量/BM25 top1 强制进入候选，防止被融合挤掉；
- 简单问题不拆，避免无谓的模型调用和延迟。

### 3.3 为什么阈值选 0.5

- 150 题上，0.1/0.3/0.5 的 Recall、正确率、拒答率一致；
- 0.5 的候选更少，P95 更低；
- 0.7 开始漏召回（跨文档召回降到 0.95，拒答率降到 0.958）；
- 结论只适用于当前 6 份文档与评测集，换模型/语料要重新扫描。

### 3.4 为什么引用要做后处理

- Prompt 约束不能保证模型一定按片段编号引用；
- 模型会把"第十条"写成 `[10]`，越界后被过滤，引用变空；
- 后处理：校验模型引用、按回答与片段重合度补齐、清理无效编号；
- 这是"生成后校验"，不增加模型调用成本。

### 3.5 为什么不继续堆功能

- 150 题已经接近饱和，继续加功能的收益无法用指标证明；
- 优先补工程化（测试、CI、Docker、日志）和失败分析；
- rerank、语义切片等优化，要等难例证明"候选有答案但排不进 topN"再做。

| 指标 | 结果 |
|---|---|
| Recall@8 | 1.000 |
| 跨文档召回 | 1.000 |
| 引用覆盖率 | 1.000 |
| 关键词正确率 | 1.000 |

## 5. 经验与教训

1. **先让评测能失败，再谈优化**：全 1.0 的评测没有区分度；
2. **阈值不是越高越好**：0.7 开始漏召回；
3. **Prompt 不能解决所有问题**：跨文档召回要靠检索层；
4. **引用是生成后的工程问题**：解析、校验、对齐缺一不可；
5. **RRF 适合多路融合**：不用调两路分数量纲；
6. **工程化也是项目能力**：单测、CI、Docker、日志能显著提升可信度。
