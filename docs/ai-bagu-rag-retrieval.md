# RAG 检索优化八股

> 面向面试复习 + 项目改造的速查文档。
> 覆盖：切片策略、查询拆解、混合检索、重排（rerank），以及本项目现状与改造路线。

---

## 0. 一页速查

| 主题 | 一句话 | 典型方案 | 代价 |
|---|---|---|---|
| 切片 | 把长文档切成可检索的小块 | 固定长度、递归字符、语义、结构感知、父子块 | 切太碎丢上下文，切太大召回差 |
| 查询拆解 | 把复杂问题拆成多个可检索的子问题 | 规则拆分、LLM 拆解、多跳 | 多次检索，延迟增加 |
| 混合检索 | 关键词 + 向量一起召回 | BM25 + Embedding + RRF | 多一路索引与融合逻辑 |
| 重排 | 对召回结果做精排 | Cross-encoder、LLM rerank | 延迟和成本增加 |

生产级常见链路：

```
查询改写/拆解
    → 多路召回（BM25 + 向量）
    → 融合去重（RRF）
    → 重排（top 20~50 → top 3~5）
    → 拼 Prompt
    → 生成 + 引用
    → 评测
```

RAG 不是必须每一步都做；先保证"召回能覆盖答案"，再谈重排。

## 1. 切片（Chunking）

### 1.1 为什么必须切片

- 大模型上下文有限，不能把整本手册塞进去；
- 检索粒度越细，向量表达越聚焦；
- 但切得太碎会丢上下文，切得太大主题不集中。

核心矛盾：**检索精度（小块） vs 上下文完整性（大块）**。

### 1.2 固定长度切片（Fixed-size）

按字符/token 数切，常见 `chunk_size=300~800`，`overlap=10%~20%`。

- 优点：简单、快、长度可控；
- 缺点：可能从句子/条款中间切断；
- 适合：结构不明显的长文本、快速基线。

我们项目当前就是这一类：700 字 + 120 overlap，按页、按段落聚合。

### 1.3 递归字符切片（Recursive）

按分隔符优先级递归切：

```
"\n\n" → "\n" → "。" → "；" → "，" → " "
```

先尽量在段落切，段落太长再按句子切，句子还长再按字符切。

- 优点：尽量保持语义单元完整；
- 缺点：中文标点/格式不统一时要调分隔符；
- 实现：LangChain `RecursiveCharacterTextSplitter` 就是这个思路。

### 1.4 句子/段落切片

按句子或自然段切，再合并到目标长度。

- 适合：新闻、说明文、问答；
- 不适合：法律条文、技术规范这种"一条就是完整语义"的文本。

### 1.5 语义切片（Semantic Chunking）

思路：**相邻句子语义相近就放一起，语义跳变就切开**。

做法：

1. 先按句子切；
2. 对每句算 Embedding；
3. 计算相邻句子的余弦相似度；
4. 相似度低于阈值（或用分位数）就在此处断开；
5. 合并过短的块，限制最大长度。

- 优点：比固定长度更贴合主题；
- 缺点：每句都要 Embedding，成本高；阈值敏感；短句/列表效果一般；
- 面试说法："语义切片用句子级向量相似度找主题边界，效果依赖阈值和文本质量，通常作为离线实验方案。"

### 1.6 结构感知切片（Structure-aware）

利用文档结构切：

- Markdown：按 `#/##/###` 标题；
- HTML：按标签层级；
- PDF：按页、栏、标题、表格；
- 法律/制度：按"第 X 条/章/节"；
- 代码：按函数/类（AST）。

优点：保留天然语义边界；缺点：需要解析文档结构。

**对本项目最值得试的改进**：法律文档按"第 X 条"切，而不是 700 字硬切。

### 1.7 父子块 / 小到大检索（Parent-Child, Small-to-Big）

- 用**小 chunk**建索引，保证检索精度；
- 命中后返回它的**父块**（更大段落/整节）给模型，保证上下文完整。

变体：

- 句子窗口检索：索引句子，命中后返回前后 N 句；
- 父子文档：子块检索，父块生成。

优点：兼顾精度与上下文；缺点：要维护两层结构。

### 1.8 上下文增强切片（Contextual Retrieval）

在切片前让 LLM 给每块补一句上下文，例如：

> "这部分来自《员工报销制度》第三章差旅报销，讲住宿标准。"

再把"上下文 + 原文"一起 Embedding。

- 优点：解决"块脱离文档后语义丢失"；
- 缺点：每块一次 LLM 调用，成本高；
- 来源：Anthropic 的 Contextual Retrieval 思路。

### 1.9 Late Chunking

先用**长上下文 Embedding 模型**对整篇文档编码，得到每个 token 的向量；再按 chunk 范围做池化，得到块向量。

- 优点：块向量自带全文上下文；
- 缺点：依赖支持长上下文的 Embedding 模型，工程复杂；
- 适合：长文档、上下文依赖强的场景。

### 1.10 命题切片 / LLM 切片（Proposition / Agentic）

- 命题切片：把文本拆成"原子事实"（每句只表达一个事实），再索引；
- LLM 切片：让模型判断在哪里断句/分块；
- 优点：语义完整、适合问答；缺点：成本高、可能不稳定。

### 1.11 特殊内容切片

| 类型 | 做法 |
|---|---|
| 表格 | 按行/按表切，保留表头；或生成表格摘要 |
| 代码 | 按函数/类切（AST），保留文件路径 |
| 问答对 | 一问一答为一块 |
| 图片/扫描件 | OCR 后再切；或用多模态模型生成描述 |
| 对话 | 按会话/话题切 |

### 1.12 参数怎么定

| 参数 | 经验 |
|---|---|
| chunk_size | 中文 300~800 字；英文 256~512 tokens |
| overlap | 10%~20%；太小会断上下文，太大会重复 |
| 最小块 | 低于 50 字可合并，避免噪声 |
| 评估 | 用同一套评测集对比 Recall@K、答案正确率、引用覆盖 |

**不要凭感觉调参**：一次只改一个参数，跑评测对比。

### 1.13 切片面试问答

**Q：chunk 越大越好还是越小越好？**
> 不是。大块上下文完整但主题分散、向量不聚焦；小块检索准但容易丢上下文。要用评测在"召回率/答案质量"之间找平衡，常见做法是父子块或小到大检索。

**Q：语义切片一定比固定切片好吗？**
> 不一定。语义切片成本高、阈值敏感；对于结构清晰的文档，结构感知切片往往更稳。固定切片是可靠基线。

**Q：overlap 有什么用？**
> 防止答案正好被切在边界上导致上下文丢失；代价是存储和检索重复。

## 2. 查询处理（Query Processing）

### 2.1 查询改写（Query Rewrite）

把用户口语化/省略的问题改成适合检索的形式：

- 补全指代："它" → "试用期工资"；
- 纠错/归一化："五险一金怎么交" → "社会保险 住房公积金 缴纳"；
- 去掉无关礼貌词："请问一下……"；
- 多轮对话中结合历史补全上下文。

实现：小模型/LLM 一次调用，或规则 + 词典。

### 2.2 查询拆解（Query Decomposition）

适合两类问题：

1. **多意图**："签劳动合同和公积金登记的时限分别是多久？"
2. **多跳**："A 公司的母公司去年营收多少？"（先查母公司，再查营收）

拆解方式：

- 规则：按"和/以及/分别/分别是什么"拆；
- LLM：让模型输出 JSON 数组 `["子问题1","子问题2"]`；
- 多跳：串行，前一题答案作为后一题输入。

并行拆解流程：

```
原问题
  → LLM 拆成 N 个子问题
  → 每个子问题独立召回
  → 结果合并去重（RRF/按文档）
  → 拼 Prompt 生成
```

代价：N 次检索 + 一次拆解调用；子问题太多会引入噪声。

**本项目第 22 题**就是典型多意图失败：一个向量被"公积金"主导，劳动合同法没召回。查询拆解是最直接的修复。

### 2.3 查询扩展（Query Expansion）

- 同义词/近义词扩展："报销" → "费用报销、差旅报销"；
- 多查询（Multi-Query）：LLM 生成 3~5 个改写版本，分别检索后融合；
- HyDE：让 LLM 先"编"一个假设答案，用假设答案的向量去检索；
- Step-back：先问一个更抽象的问题，再回到具体问题。

HyDE 适合"问题很短、文档表述不同"的场景，但可能引入假设错误。

### 2.4 查询路由 / Self-Query

- 路由：判断问题该查哪个知识库/工具（制度库、产品库、工单库）；
- Self-Query：从问题中抽取元数据过滤条件，如"2025 年之后的报销制度" → `year >= 2025`。

### 2.5 拆解结果的融合

- 去重：按 chunk_id / 文档 + 页码；
- 融合：RRF（推荐，简单稳）、按分数加权、按子问题轮询；
- 截断：每个子问题取 topK，合并后再重排/截断，避免 Prompt 爆炸。

### 2.6 查询处理面试问答

**Q：什么时候需要查询拆解？**
> 问题包含多个意图、多个实体对比，或需要多跳推理时。简单单意图问题不需要，拆了反而增加延迟和噪声。

**Q：拆解后多个子查询结果怎么合并？**
> 先按 chunk/文档去重，再用 RRF 或加权分数融合，最后统一重排截断。

**Q：HyDE 的原理和风险？**
> 先生成假设答案再检索，能缓解"问题与文档表述不一致"；风险是假设答案本身错误，会把检索带偏。

## 3. 混合检索（Hybrid Retrieval）

### 3.1 稀疏 vs 稠密

| | 稀疏检索（BM25） | 稠密检索（Embedding） |
|---|---|---|
| 原理 | 词频/逆文档频率 | 向量空间语义相似 |
| 强项 | 专有名词、编号、数字、精确词 | 同义改写、语义相近 |
| 弱项 | 同义词/改写 | 罕见词、数字、条款号 |
| 代表 | BM25、BM25+、SPLADE | text-embedding、BGE、E5 |

两者互补，所以生产上常用混合检索。

### 3.2 BM25 公式（理解即可）

```
score(q,d) = Σ IDF(term) * (tf * (k1+1)) / (tf + k1*(1-b+b*|d|/avgdl))
```

- `tf`：词在文档中出现次数；
- `IDF`：词越稀有越重要；
- `k1`、`b`：调节词频饱和与长度归一化。

不需要手推，知道"稀有词权重高、长文档要归一化"即可。

### 3.3 融合方法

**RRF（Reciprocal Rank Fusion，推荐）**：

```
score(d) = Σ 1 / (k + rank_i(d))
```

- `rank_i(d)`：文档在第 i 路结果中的排名；
- `k` 常取 60；
- 只看排名，不看原始分数，避免两路分数量纲不一致。

**加权分数融合**：

- 先 min-max 归一化两路分数；
- `final = α * vector_score + (1-α) * bm25_score`；
- α 需要评测调。

### 3.4 中文分词

BM25 依赖分词：

- Elasticsearch：IK 分词器；
- PostgreSQL：`zhparser` / `pg_jieba` 扩展，或 `pg_trgm` 做模糊匹配；
- 应用层：jieba 分词后自己算 BM25。

中文不分词直接按字，效果通常很差。

### 3.5 在本项目怎么落地

方案 A（轻量）：

- PostgreSQL 加 `tsvector` 全文索引（需要中文分词扩展）；
- 向量检索 + 关键词检索各取 top 20；
- Java 里做 RRF 融合，取 top 5。

方案 B（工程化）：

- 引入 Elasticsearch（你之前的社区项目用过）；
- ES 做 BM25，pgvector 做向量；
- 两路召回 → RRF → 重排。

先做 A，够面试讲；B 作为扩展。

### 3.6 混合检索面试问答

**Q：BM25 和向量检索有什么区别？**
> BM25 是词袋匹配，依赖精确词和分词，擅长专有名词/编号；向量检索是语义匹配，擅长同义改写。两者互补，所以混合使用。

**Q：RRF 为什么有效？**
> 它只用排名不用原始分数，避免不同检索器分数量纲不一致；多路都靠前的文档会被加权，鲁棒性好。

**Q：混合检索一定比单路好吗？**
> 不一定。如果语料和问题都很口语化、语义匹配为主，向量已经够；混合会增加索引和融合复杂度，要用评测验证。

## 4. 重排（Rerank）

### 4.1 为什么需要重排

向量召回是"粗排"：

- 双塔模型（query 和 doc 分别编码）快，但交互不充分；
- topK 里常混入语义相近但不回答问题的片段。

重排用更强的模型对"问题-片段"做精细打分：

```
向量召回 top 50 → rerank → top 5 → 生成
```

### 4.2 常见方案

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| Cross-encoder | query+doc 拼一起过模型打分 | 精度高 | 慢，只能对小候选集 |
| BGE-reranker | 中文开源 cross-encoder | 可本地部署 | 需要 GPU/模型服务 |
| Cohere/百炼 Rerank API | 托管服务 | 接入快 | 按调用收费 |
| LLM 重排（pointwise） | 让 LLM 给每个片段打分 | 灵活 | 贵、慢、不稳定 |
| LLM 重排（listwise） | 一次给多个片段排序 | 效果好 | 上下文长度限制 |
| ColBERT / late interaction | token 级交互 | 精度与速度折中 | 工程复杂 |

### 4.3 流程与参数

```
召回 top 30~100
  → 截断每段长度（如 512 tokens）
  → rerank 打分
  → 取 top 3~5
  → 拼 Prompt
```

- 候选太多：延迟高；
- 候选太少：重排没意义；
- 常见候选 20~50，最终 3~5。

### 4.4 怎么评估

- 端到端：答案正确率、引用覆盖、P95 延迟；
- 检索层：Recall@K、nDCG@K、MRR；
- 成本：rerank 调用次数 × 单价。

### 4.5 重排面试问答

**Q：重排和召回的区别？**
> 召回从全库快速找候选（重召回），重排对少量候选精细打分（重精度）。召回追求"别漏"，重排追求"排得准"。

**Q：为什么不能直接对全库重排？**
> cross-encoder 要逐对计算，全库成本不可接受；所以先向量/BM25 粗排到几十条，再重排。

**Q：重排一定提升效果吗？**
> 通常提升精度，但如果候选里根本没有正确答案，重排也救不了；所以召回率是前提。

## 5. 生产级 RAG 完整链路

```
【离线】
文档接入 → 解析 → 清洗 → 切片 → 向量化 → 建索引（向量/关键词）
                              ↘ 元数据（标题/来源/时间/权限）

【在线】
用户问题
  → 查询改写 / 拆解 / 路由
  → 多路召回（向量 + BM25）
  → 融合去重（RRF）
  → 重排（可选）
  → 阈值/长度控制
  → Prompt（编号 + 引用规则 + 拒答规则）
  → 大模型生成（流式）
  → 引用校验/对齐
  → 日志、评测、反馈
```

## 6. 本项目的现状与改造路线

### 6.1 现状

| 环节 | 现状 |
|---|---|
| 切片 | 700 字 + 120 overlap，按页/段落 |
| 向量化 | text-embedding-v3，1024 维 |
| 召回 | pgvector 余弦，topK=5，阈值 0.1 |
| 查询处理 | 无 |
| 混合检索 | 无 |
| 重排 | 无 |
| 生成 | qwen-plus，温度 0.2，SSE |
| 引用 | 解析 + 对齐 + 清理越界编号 |
| 评测 | 30 题，Recall@8=1.0，跨文档 0.8，引用覆盖 0.96 |

### 6.2 改造优先级

1. **查询拆解**：解决多意图跨文档（第 22 题），成本最低、收益直接；
2. **混合检索**：BM25 + 向量 + RRF，提升专有名词/条款号召回；
3. **重排**：候选扩到 20~30，再 rerank 到 5；
4. **切片优化**：法律文档按"第 X 条"切，配合评测对比；
5. **阈值/topK 调优**：用评测集找平衡。

每次只改一个变量，跑同一套 30 题评测，记录：

- Recall@K；
- 引用覆盖；
- 答案正确率；
- 拒答率；
- P95 延迟；
- 单次成本。

## 7. 常见失败模式与排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 召回不到答案 | 切片太大/太小、Embedding 不匹配、查询表述差异 | 调切片、混合检索、查询改写 |
| 召回了但不回答 | 阈值过高、Prompt 约束太强 | 调阈值、检查 Prompt |
| 答非所问 | 噪声片段太多、topK 太大 | 重排、降 topK、阈值 |
| 编造引用 | 模型没按格式、引用编号越界 | 引用对齐、结构化输出、校验 |
| 多文档问题只答一半 | 单查询向量被一个意图主导 | 查询拆解 |
| 延迟高 | 候选太多、重排/LLM 调用多 | 控制候选数、缓存、并行 |
| 新文档不生效 | 没重建索引/缓存 | 检查状态、重建、缓存失效 |

## 8. 高频面试题速答

**Q：RAG 的完整流程？**
> 离线：解析、切片、向量化、建索引；在线：查询处理、召回、重排、拼 Prompt、生成、引用、评测。

**Q：切片策略有哪些？**
> 固定长度、递归字符、句子/段落、语义切片、结构感知、父子块、上下文增强、Late Chunking、命题/LLM 切片；特殊类型还有表格、代码、问答对。

**Q：语义切片怎么做？**
> 句子级 Embedding，计算相邻句相似度，低于阈值就断开，再合并过短块、限制最大长度。

**Q：查询拆解怎么实现？**
> 规则或 LLM 把多意图/多跳问题拆成子问题，分别召回后去重、RRF 融合，再统一生成；多跳场景可以串行。

**Q：混合检索怎么融合？**
> BM25 和向量各取 topN，用 RRF（按排名）或归一化加权分数融合，再重排/截断。

**Q：重排模型怎么选？**
> 中文可用 BGE-reranker 本地部署；要快接可用托管 Rerank API；LLM 重排灵活但贵且慢。候选 20~50，最终 3~5。

**Q：RAG 效果怎么评估？**
> 检索层看 Recall@K、nDCG/MRR；生成层看答案正确率、引用覆盖、拒答率；工程层看 P95 延迟和成本。

**Q：RAG 和微调怎么选？**
> 知识频繁更新、需要引用溯源 → RAG；要改变模型风格/领域能力 → 微调；两者可以结合。
